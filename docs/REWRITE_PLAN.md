# 截图库重写建议：固定上游对齐与本库额外工作

日期：2026-10-26。状态：设计与验收建议，尚未实施运行时代码重写。
本库参考为 `8650535` 所记录的源码版本 3.0.0 / C ABI 2；具体问题与代码依据见 [改进清单](OPTIMIZATION_RECOMMENDATIONS.md)。
新项目 **maafw-screencap** 的抽取范围、架构、接口、阶段与交付安排见 [抽取与扩展计划](maafw-screencap-extraction-plan.md)；本文件保留分类依据和重写原则。

## 1. 固定基线与目标

本计划的上游仅指 MaaFramework `0fc6025c2fc224a171b57d89505e8d47acd2a8b1`，不指最新主线。
对应 MaaUtils 子模块固定为 `f8994a38ddc6858800dfea8a04e958a0adbfb184`；实际构建时另记录 OpenCV、SDK 和系统依赖版本。
`b8d1550` 已存在本库移植差异，只可作历史参考。PR #1587 在本轮核对时未合并，不能当作固定上游已具备的行为。

“完美对齐的提取库”指忠实保留该上游的拟保留功能、算法、默认值和可观察行为，且移植不引入额外错误；
这不意味着上游没有缺陷，也不自动包含本库新增的目标、元数据、策略和 ABI。

重写分为两部分：

- **上游行为对齐**：以固定源码、对照程序和场景矩阵证明哪些行为一致，哪些存在有意差异。
- **本库额外工作**：进一步区分必要的正确性/契约修复、可维护性改进、可选能力和需要测量的性能优化。

修复从上游继承的问题属于额外正确性工作，不应冒称“追随上游已有修复”；安全和像素正确性问题也不因起源在上游就变成可选优化。

## 2. A、B、C 三批的边界

| 批次 | 目标 | 本轮条目 | 放行条件 |
| --- | --- | --- | --- |
| A：上游行为对齐 | 恢复并证明固定上游行为 | 已编号建议中主要为 F1 的行为部分；完整重写还须建立全后端对齐矩阵 | 行为对照通过，未对齐项明确列出，不作零遗漏保证 |
| B：正确性与契约修复 | 保证像素、资源、状态与已启用能力的正确性 | F2–F5、B1–B6、L1/O1，F1 的安全实现适配，必要错误与回归处理 | 对应边界与失败回归通过，失败不能伪装为成功或静默降级 |
| C：维护与性能优化 | 改善理解、维护和经测量确认的成本 | M1–M5 的维护部分、T1–T4 | 维护改动保持行为；性能改动有可比较数据和正确性门禁 |

A、B 按风险与依赖安排，不机械规定 A 全部结束才能做 B。
M4 的主要/清理错误因果保留和 M5 的必要回归随 A/B 修复交付；它们不能等到“有时间再整理”。

可选能力与可选性能工作是两回事。例如 fresh-only、取消和严格后台是否加入新库可以选择；
一旦允许调用者启用，就必须兑现声明的契约，相关缺陷属于 B。

## 3. A：F1 的行为对齐与全面基线验收

固定上游 [PseudoMinimizeHelper.cpp](https://github.com/MaaXYZ/MaaFramework/blob/0fc6025c2fc224a171b57d89505e8d47acd2a8b1/source/MaaWin32ControlUnit/Screencap/PseudoMinimizeHelper.cpp) 表明：

1. 暂停截图期间仍有独立观察，约每 100ms 检查目标激活并恢复窗口。
2. 伪最小化目标成为前台即可协调恢复，不强制要求新键鼠输入。
3. 配套的暂停取图、无新输入的程序激活、其他窗口切换回归，以及文档修正属于对齐验收。

共享观察状态、共享租约、锁顺序、异常恢复和退出生命周期是安全实现这些目标的本库适配，归 B。
可选择事件驱动或有界轮询，不要求复制上游线程结构；也不能直接采用历史 b8 中普通 bool 共享状态的实现。
现有 HWND 生命周期验证、原属性恢复、按位所有权和失败报告继续保留。

如果保留当前的恢复后前台快照/输入时间过滤，即使补回独立观察器，也应记录为恢复判据与上游仍有差异。
只有恢复条件和暂停期间观察均通过，才可说明该行为项对齐。100ms 是上游检查周期，不能宣传成硬实时上限。

完整基线验收不能只测 F1。还应覆盖各后端像素/几何、前台回退与冷却、FramePool 清队列和超时回放、
PipeWire 回放/停流、候选测速和 None/default 方法语义，以及失败和资源副作用。
像素转换、异常输入和窗口状态要分别验证，不能只凭函数文本相近或主流程成功断言全库一致。

## 4. B：必要的正确性、边界与契约修复

### 4.1 分类与来源

| 条目 | 修复内容 | 与固定上游的关系 |
| --- | --- | --- |
| F1 的实现适配 | 共享观察、租约、锁顺序、退出及恢复失败处理 | 安全实现 A 的方式，不要求线程结构相同 |
| F2 | 旧帧保留原采样身份，正确表达 NEW/REUSED/UNKNOWN 和年龄 | 上游已有回放；新增采样/新鲜度契约须由本库正确衔接 |
| F3 | Memfd 尺寸溢出、缩窄及 PipeWire 长度/stride/offset/映射检查 | 固定上游也存在相关边界缺口，是修复继承问题 |
| F4 | 重新协商后废弃旧格式帧，按相应代次发布 | 固定上游同样更新格式描述而保留旧帧，是额外正确性修复 |
| F5 | YUY2 与上游实际调用的 OpenCV 转换结果一致 | 修复本库自定义图像适配偏差，不是修复上游同一错误 |
| B1 | 日志接收器配置、并发和异常边界 | 针对本库日志基础设施 |
| B2 | 全链路剩余预算、取消、FramePool 权限等待、错误及时唤醒 | 兑现本库新增的 deadline/cancellation 能力，不冒称所有 OS 调用可硬中断 |
| B3 | Wayland 版本上限、必需协议、代理创建检查和输出移除 | 固定上游也有检查不足，属于协议健壮性修复 |
| B4 | PipeWire 全局 init/deinit 所有权与配平 | 固定上游同样构造 init、析构只 close；需按依赖版本与共享引用处理 |
| B5 | 六语言绑定部分注册失败后的回滚 | 针对本库绑定资源生命周期 |
| B6 | 原生回调异常兜底、缓冲归还与错误唤醒 | 对事件回调边界的额外健壮性修复 |
| L1 | 区分停流、暂停、资源释放、会话关闭、销毁及各代次 | 本库公开生命周期契约需要单独定义 |
| O1 | 可写交付帧不污染内部缓存或其他持有帧 | 本库所有权正确性要求，优先于 T1 减少复制 |

固定源码依据：[PipeWire](https://github.com/MaaXYZ/MaaFramework/blob/0fc6025c2fc224a171b57d89505e8d47acd2a8b1/source/MaaLinuxControlUnit/Screencap/PipeWireScreencap.cpp)、
[MemfdBuffer](https://github.com/MaaXYZ/MaaFramework/blob/0fc6025c2fc224a171b57d89505e8d47acd2a8b1/source/MaaLinuxControlUnit/Base/MemfdBuffer.cpp)、
[WaylandClient](https://github.com/MaaXYZ/MaaFramework/blob/0fc6025c2fc224a171b57d89505e8d47acd2a8b1/source/MaaLinuxControlUnit/Wayland/WaylandClient.cpp)。

### 4.2 两个不能混入修复的默认行为变更

- **PipeWire 超时旧帧回放**：固定上游已有该行为。F2 可以保留它，只纠正采样身份与新鲜度判断；默认禁止回放须另作产品决定。
- **PipeWire inactive 只停流**：固定上游保留会话。L1 必须明确接口承诺，但不自动要求改成停用即销毁会话。

F4 的格式变化失效、断流/权限错误拒绝错误来源缓存，是必要正确性边界，不能用“保留上游回放行为”作为交付无效旧帧的理由。

### 4.3 生命周期和元数据应共同设计

每个后端交付内部结果时，携带取样时的来源、格式、样本身份和适用的会话代次，明确是新取样、复用还是未知。
公共层不能仅因收到一个 Image 就统一推断 NEW，也不能把转换/交付时间当成所有后端的原采样时间。
内容变化、游戏渲染时间与库侧取样时间分别表达，缺少证据时保持未知。

协商结果变化时清理不再适用的 latest/pending/cache，并推进相应代次；关闭或重连时拒绝晚到旧代次结果。
已交付 Frame 可以继续独立读取，但它的存活不代表可以作为新会话缓存使用。
错误回调需要保存终止原因并唤醒等待者；等待状态要能区分成功、失败、取消和断开。

缓冲校验应在缩窄转换、映射和 memcpy 之前完成；C/系统回调异常边界和资源归还应覆盖失败与早退。
与这些正确性条件对应的测试随修复交付，不能等性能阶段再补。

## 5. 当前值得继承的额外保证

继承契约与经过验证的结果，不要求照搬现有类布局、长函数和历史创建入口。

| 当前工作 | 重写建议 | 注意边界 |
| --- | --- | --- |
| 显式目标、来源/几何/身份校验 | 强烈建议保留 | 与纯上游的目标/default 选择行为有差异，应有清晰接口或兼容决策；前后采样不是 OS 原子事务 |
| 独立帧、回调释放协议、长度校验 | 作为核心所有权契约 | O1 必须验证可写别名；共享引用只保证存活 |
| 同窗口共享租约与安全恢复 | 保留并补齐 A 的独立焦点恢复 | 不扩张为所有 Manager 调用天然并发安全 |
| 候选事务、正式重验、首帧保留 | 保留正确性目标 | 上游已经有自动测速和按需构造，真正的增量是隔离、重验和交付协调 |
| 严格后台、DXGI 缓存、fresh-only/年龄 | 可选能力，但启用后其契约必须正确 | 不以抢焦点后切回冒充后台；缓存不能掩盖设备/权限/来源错误 |
| 共享 deadline 与独立取消信号 | 根据使用需求选择，按平台兑现 | 区分可协作等待、返回后拒绝晚到结果和不能硬中断的调用 |
| 结构化错误、能力查询、限量诊断 | 建议从初期建立 | 错误因果和异常边界属于 B，日志与诊断本身不能成为新失败入口 |
| SDK 消费、生成声明、源码重建与来源哈希 | 作为工程交付基础 | 编译/分发检查不能替代桌面运行验收；绑定数量按实际消费者需求安排 |

当前代码中已存在的 DXGI 映射期复制、明确 DIB 读取和原生几何等修复可以逐项迁移，
但不能仅因为代码在当前版本存在，就宣称各平台完整实机验收通过。

## 6. 职责分层与 A/B/C 工作分类分别使用

建议的实现职责仍可分为：

1. **后端层**：平台调用、原生事件、帧获取和缓冲释放；记录与固定上游的来源对应关系及有意修复。
2. **核心协调层**：目标身份、格式/会话代次、帧所有权、窗口租约、候选事务、错误和发布校验。
3. **策略与接口层**：后台约束、缓存/新鲜度、时限/取消、能力协商与绑定。

这三个层次不等同于 A/B/C。后端层也必须实施 B 的安全修复；策略层的能力正确性也属于 B，不能整体称为可选优化层。
归类时同时记录“改动在哪一层”和“为何改动”，便于检查是否不慎改变上游行为。

## 7. C：维护整理和性能工作

| 条目 | 实施边界 |
| --- | --- |
| M1：格式/注释 | 纯格式与逻辑改动分开，生成文件由生成器处理；注释必须说明真实所有权 |
| M2：状态/锁关系说明 | 状态不变量和锁/退出安全随 B 实现，补充说明与结构整理归维护工作 |
| M3：常量生成 | 自动化契约维护；不替代必要的 ABI 布局、功能位和可选符号验证 |
| M4：函数拆分 | 按候选/激活/发布阶段整理；主要与清理错误因果保留随相关 B 修复交付 |
| M5：测试诊断 | 场景、方法、阶段和预期/实际更易定位；必要回归随 A/B 交付 |
| T1：减少复制 | 先通过 O1 和缓冲生命周期回归，再比较复制次数、分配量与耗时 |
| T2：减少来源查询 | 保留独立前后校验、目标身份与布局变化拒绝，不直接以 TTL 替代 |
| T3：FramePool 事件唤醒 | 先保证通知生命周期、退出和不丢更新，再比较 CPU/唤醒数与延迟 |
| T4：选择与持续性能 | 明确单次冷启动排序和持续性能的区别，测量后再决定是否引入新策略 |

性能比较固定来源、像素格式、策略和负载，记录连接/首帧/持续延迟、CPU、线程/句柄、内存和采样年龄。
不能把删掉必要复制、跳过来源校验或放宽失败判据形成的数据称为等价条件下的优化收益。

## 8. 交付与验收

1. **基线准备**：保存固定源码与依赖身份、建立行为/副作用矩阵，列出当前已有保证和计划差异。
2. **A/B 按风险分批**：分别交付 F1 行为及其安全实现、像素/缓冲、采样/格式代次、回调/生命周期与能力兑现；每批携带必要回归。
3. **维护整理**：在对应行为和失败路径已有门禁后，按小范围实施 M；不把必要测试和错误处理延期。
4. **性能选择**：T 先测量，再对有稳定收益的条目实施并复核正确性。

A 的焦点测试在停止库调用后，直接读取 Win32 状态确认恢复，避免查询库时顺带触发恢复而误通过。
B 覆盖旧帧回放、重新协商后无新帧、短缓冲/越界偏移、代理创建失败、分配/回调异常、错误唤醒、取消与停机竞争，以及可写帧污染缓存。
危险输入可先在安全替身与隔离测试中验证，不要求正常运行路径保留危险实现来证明忠实。

共享状态、代次和算术边界可做便携测试；Win32/PipeWire/Wayland/macOS 的真实事件和资源语义须由适用环境运行验证。
本轮不使用 WSL；三平台编译、SDK/wheel 和源码包验证不能替代各自桌面矩阵。未执行的项目继续列为未验证。

每项差异记录固定上游行为、本库行为、分类、理由、兼容影响和证据。
A 通过不代表 B 已完成，C 的性能结果不能替代 A/B；修复中的必要功能与正确性不以性能收益为成立条件。

## 9. 重写前需要保留为显式决策的事项

- 旧 C ABI/绑定是否兼容；若需要兼容，适配层独立管理，不使后端承受全部历史入口约束。
- 默认缓存回放、None/Auto、严格来源/几何拒收及前台方法的行为；不得在结构重构中默默改变。
- inactive 的公开含义、重新使用是否要 reconnect，以及新增 pause/release/close 操作是否有必要。
- 哪些平台与可选策略在首版承诺支持；未具备的能力明确拒绝，不能静默按弱保证执行。

这些是后续设计决策，不构成本轮实现授权，也不恢复此前取消的版本标签流程。
